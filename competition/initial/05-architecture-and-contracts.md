# 05 · 架构与契约（Architecture & Contracts）

## 1. 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│  用户入口：岗位/JD/简历/证据/导出                             │
├─────────────────────────────────────────────────────────────┤
│  AgentTeams 编排层（主控 Orchestrator）                       │
│  任务拆解 · 阶段路由 · 上下文编排 · 状态追踪 · 升级决策        │
├─────────────────────────────────────────────────────────────┤
│  多 Agent 协同层                                             │
│  JobRequirementAnalyst · EvidenceCurator                     │
│  ResumeStrategist · QualityDeliveryGuardian                  │
├─────────────────────────────────────────────────────────────┤
│  Skill 能力层（见 04）                                        │
│  材料校验 · JD 决策地图 · 事实检索 · 补证 · 改写 · 门禁 · Trace │
├─────────────────────────────────────────────────────────────┤
│  连接器契约层（MCP 等价，见 3）                               │
│  DirectLLM / Mock / 导入解析 / 导出 / 存储                    │
├─────────────────────────────────────────────────────────────┤
│  证据与治理层                                                │
│  共享状态（ResumeDocument/Zustand、Career Domain/IndexedDB）   │
│  Studio Trace（可回放）· Zod 校验 · 评测                      │
└─────────────────────────────────────────────────────────────┘
```

## 2. AgentTeams 映射

| AgentTeams 能力 | 本项目映射 | 落地方式 |
| --- | --- | --- |
| 角色编排 | 主控按「分析/补证/制作/交付」四阶段路由 4 个 Agent | 主控只做路由，不直接写业务数据 |
| 任务拆解 | JD→需求地图→事实匹配→补证→优化→交付 子任务链 | 阶段门禁控制流转 |
| 上下文传递 | `requirementId` / `claimId` / `traceId` + 共享岗位文档与事实引用 | 稳定 ID 贯穿引用链，避免裸文本上下文 |
| 协同执行 | 依赖图：需求确认→匹配；缺口→补证→重匹配；诊断→（可选）面试策略 | 过期传播锁定下游 |
| 状态追踪 | 节点状态（待处理/运行/成功/失败）+ 门禁状态（候选/待复核/已确认/已过期） | workflow state + Trace 关联 |

## 3. 连接器契约（MCP 等价方案）

> 本阶段不实现 MCP Server，但按手册 9.2 提供等价连接器契约；后续迁移到 MCP 只需协议适配（工具 → MCP Tool，参数 Schema 不变），无需重做调用链。

| 字段 | 内容 |
| --- | --- |
| 协议 | HTTP/JSON（服务端调用），统一 `{name, params}` 入参、`{ok, data|error}` 返回 |
| 鉴权方式 | 用户自配 API Key；密钥仅存于浏览器本地，不进仓库/备份/演示材料 |
| 输入输出 Schema | 每个工具以 Zod 定义参数与返回结构（如 JD 解析、匹配、优化、导出） |
| 错误处理 | 超时（分析单次 60s / 一般 120s）、主动取消、调用次数预算、分类错误 |
| 审计记录 | 每次调用写入 Studio Trace（promptId、runId、耗时、失败） |
| 幂等控制 | 门禁类工具只读、导出由状态门禁保证幂等 |
| 降级方式 | DirectLLM 主路径 ↔ Mock 离线可复现路径，共用同一 Schema |
| 迁移成本 | 仅需协议适配层（HTTP→MCP），参数 Schema 与 Skill 不变 |

工具清单（现有可验证）：JD 结构化解析、匹配、优化、补证、面试策略、导入解析（PDF/DOCX）、DOCX 导出、ATS 评分、最终定稿、证据追溯。

## 4. RAG 替代说明（手册 9.4）

> 本方案不采用「知识库 RAG」，以结构化事实 + 稳定 ID + 确定性筛选 + 来源关系代替。依据手册 9.4，在「Agent 记忆存储 / 知识库 RAG / 共享状态管理 / 轨迹可观测」四项中，除知识库 RAG 外已覆盖 2 项：

| 能力 | 是否实现 | 落地 |
| --- | --- | --- |
| 共享状态管理 | ✅ | ResumeDocument（Zustand 持久化）+ Career Domain（IndexedDB），并发下由状态版本控制一致性 |
| 轨迹可观测 | ✅ | Studio Trace 持久化执行轨迹与证据链，支持回放与审计 |
| Agent 记忆存储 | 部分（复赛） | 事实库即长期结构化记忆；会话级记忆归入复赛 |
| 知识库 RAG | 不采用 | 以结构化事实 + 稳定 ID + 确定性筛选 + 来源关系代替 |

有效性论证：求职事实是低基数、高可信的结构化数据，用 `claimId` 精确引用与确定性筛选比向量召回更可靠、可审计，且避免 RAG 幻觉与无法定位来源的问题。
