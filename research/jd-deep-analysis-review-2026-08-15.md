# JD 深度解析审查与下一版建议

> 日期：2026-08-15
>
> 范围：Resume Expert `v1.9.4` 的 JD 拆分、岗位画像、事实匹配、页面呈现与评测体系。
>
> 方法：代码审计 + AI 产品顾问团视角 + 领域建模 + O*NET / ESCO 一手资料核验。本报告只提出方案，不修改产品代码。

## 1. 结论

当前实现已经不是“把 JD 丢给模型做摘要”，它具备原文位置、原子要求、原文引用、明示/推断/未知、事实 ID 校验和结构化输出等正确骨架。

但用户觉得“不够到位”是准确的。问题不是字段太少，而是系统尚未稳定回答五个真正有用的问题：

1. 这个岗位最核心的业务使命和交付结果是什么？
2. 哪些条件是真正的准入门槛，哪些只是偏好、背景或招聘话术？
3. 日常工作、能力、知识、工具、经验和工作情境分别是什么？
4. 哪些结论是原文明示，哪些只是推断，推断还有哪些替代解释？
5. 对当前用户而言，应该保留什么、补什么、问招聘方什么、准备哪段经历？

因此下一版不应继续堆 Prompt，而应先修复数据与评测错误，再把输出从“信息展示”升级为“求职决策地图”。

## 2. 顾问团讨论纪要

### 共识

- **《AI Engineering》视角**：没有能实际运行解析器的私有评测集，就无法证明“深度”得到提升。当前 `eval:jd` 只验证 8 条测试定义自身，不验证系统输出。
- **Karpathy 视角**：原文切分、否定词、显式优先级、引用范围、ID、覆盖率和合并必须属于 Software 1.0；原子语义拆解与有限推断才交给 LLM。关键门禁不能依赖模型自觉。
- **Cagan 视角**：用户不需要看更多分析字段，而需要更快回答“值不值得投、我最缺什么、应该怎么准备”。页面必须以决策顺序组织，而不是按后端对象顺序堆卡片。

### 分歧

- 工程视角会优先提高 Schema、引用和指标严谨度；产品视角认为，即使这些全部正确，若用户仍要自己阅读 40 条要求再总结，价值风险依然没有解决。
- 领域模型可以继续细化，但本地个人版不需要一次引入完整职业本体。先做清楚的内部分类和稳定引用；ESCO / O*NET 只作为规范词汇参考，不在本版引入 RAG。

### 综合判断

先建立可测量的岗位要求模型，再做用户可读的四层结果页。没有评测基线时不继续扩充模型输出；没有用户决策入口时不继续扩充页面字段。

## 3. 当前实现中值得保留的部分

- [`splitJDSourceItems`](../src/lib/jd/deep-analysis.ts) 保存原文偏移，长单段文本可按句号和分号拆分。
- [`assembleRequirements`](../src/lib/jd/deep-analysis.ts) 验证 `sourceQuote` 是否存在于对应原文条目。
- [`createCompactJDModelResultSchema`](../src/lib/ai/schemas.ts) 要求每个原始条目被分类，并阻止模型引用不存在的条目 ID。
- [`validateMatchReferences`](../src/lib/jd/deep-analysis.ts) 会删除模型创造的事实 ID 和不存在的简历引用。
- [`runLLMResumeAnalysis`](../src/services/ai/resumeAgent.llm.ts) 对 JD、匹配和岗位概览进行分阶段执行，并在成功前不写入部分结果。
- [`JDAnalysisStep`](../src/components/steps/jd-analysis-step.tsx) 已经区分原子要求、岗位推断边界和原文覆盖。

这些基础不应推倒重写。

## 4. 需要优先修复的真实问题

### P0：结果会误导用户

#### 4.1 核心能力重要性按数组位置生成

[`summarizeRequirementMap`](../src/lib/jd/deep-analysis.ts) 将关键词列表前 4 个标为高、接下来 4 个标为中，其余标为低。这个顺序来自模型输出和批次合并，不是岗位重要性证据。

结果是页面中的“核心能力表”看起来很确定，实质没有评分依据。应删除这种位置式重要性，改为由显式措辞、重复要求、职责关联、结果关联和用户确认构成可解释排序。

#### 4.2 “隐性要求”实际等于所有非 must 要求

当前把 `preferred` 和 `context` 全部汇总为 `implicitRequirements`。明确写着“优先”的条件并不隐性，工作背景也不是隐性要求。

应把“显式偏好”“工作情境”“系统推断”分开；推断不能混入原文要求列表。

#### 4.3 引用待复核的要求仍进入关键词与能力汇总

主流程只用 `validatedRequirements` 做事实匹配，却用全部 `requirements` 生成职责、硬要求、关键词和能力。这意味着引用未通过校验的要求仍可出现在 JD 结论和 ATS 输入中。

所有面向用户和下游流程的结论必须只使用已校验要求；待复核项应进入单独审核区。

#### 4.4 分批诊断分数合并方式不成立

[`mergeDiagnosisMatchResults`](../src/services/ai/resumeAgent.llm.ts) 对每批 `overallScore` 做简单平均。13 条要求拆成 12 条和 1 条时，最后 1 条与前 12 条权重相同；维度分则只保留同名维度第一次出现的结果。

诊断分不能由批次模型自报后平均。应从逐条匹配结果按明确权重确定性计算；模型只返回证据和理由。

### P1：分析深度不足

#### 4.5 原始条目覆盖不等于原子要求覆盖

Schema 能保证每条原文被分类，却不能保证分类为 `requirement` 的原文至少产生一个原子要求，也不能证明复合要求全部拆出。模型可以分类完整但漏掉一半能力，仍通过校验。

需要建立 `sourceItem -> atomIds` 覆盖关系，并对遗漏、重复、否定误判和过度拆分分别计数。

#### 4.6 引用存在不等于语义受引用支持

目前只验证 `sourceQuote` 是原文子串。模型可以引用一个真实短语，同时生成原文没有表达的结论。

需要把要求拆成“原文跨度、规范化表述、解释状态”三层；用户可看到原文与解释的差异。解释无法由原文推出时进入待复核，而不是只看字符串是否存在。

#### 4.7 优先级没有判定依据

`must | preferred | context` 只有结果，没有 `priorityBasis`。用户无法知道它来自“必须/优先”等明确措辞，还是模型判断。

优先级至少应记录：显式措辞、职责/结果关联、重复程度、标题/章节位置和模型建议。模型建议不能单独产生“必须”。

#### 4.8 九类岗位推断被强制填满

岗位概览要求模型始终返回九个主题。缺少信息时会产生大量重复的“信息不足”，有信息时 `evidence` 只是自由文本，不要求关联 `sourceItemId` 或原文跨度；`confidence` 也没有固定 rubric。

应只返回有决策价值的假设或未知项，并绑定原文引用。每条推断同时给出至少一个替代解释，避免把单一路径包装成高置信度结论。

#### 4.9 全局 Top 12 事实会饿死长尾要求

当前先把全部岗位要求拼成一个大文本，再从事实库选全局前 12 条。高频关键词会占满候选，某个关键但用词不同的要求可能没有任何事实进入模型上下文。

应按 `requirementId` 分别召回，再做总量分配：每条至少保留 0–3 个候选，高优先级要求优先，最后再控制全局上下文预算。

#### 4.10 事实强度仍由模型决定

只要存在一个合法事实 ID 或简历短引用，服务端就保留模型给出的 `strong | medium | weak`。但“提到过同一个词”不等于强证据。

证据强度应由确定性 rubric 计算：角色边界、独立程度、复杂度、行动、结果、完整指标和跨经历复现；模型只解释语义相关性。

### P2：可用性和可维护性不足

- 要求 ID 按模型返回顺序生成，重新分析或批次变化会改变 ID，不利于对比和缓存。
- 批次结果只做数组拼接，没有语义去重和跨批一致性检查。
- 页面显示 `must`、`work-focus` 等内部英文值，且要求、推断、原文、职责、关键词和能力重复展示。
- 未知项没有关联具体要求或推断，无法说明“补充它会改变哪个结论”。
- 没有识别自相矛盾、职责范围过宽、资历与职责不一致、否定条件、模糊量词和缺少成功指标等 JD 质量风险。

## 5. 建议的领域模型

不要继续把所有信息塞进当前 `JobRequirement`。建议使用以下分层概念：

### 5.1 `JDSourceSpan`

原文事实层，保存 section、start/end offset、原文、语言和结构角色。任何解释都必须引用一个或多个 span。

### 5.2 `JDRequirementAtom`

一条最小、可单独判断的要求：

- `kind`：task、deliverable、knowledge、skill、tool、experience、education、credential、industry、collaboration、work-context、constraint。
- `modality`：required、preferred、optional、informational、negated。
- `normalizedText`：规范化要求。
- `object`：作用对象或业务领域。
- `expectedBehavior`：候选人需要做什么。
- `expectedOutcome`：期望产出或结果；原文未给出则为 null。
- `proficiencySignal`：了解、可独立、熟练、主导或未知。
- `priority` 与 `priorityBasis[]`。
- `sourceSpanIds[]` 和 `interpretationStatus`。

### 5.3 `RoleHypothesis`

所有岗位本质、工作重心、团队痛点、汇报关系和隐性期望都属于假设层：

- `conclusion`
- `sourceSpanIds[]`
- `confidenceBasis[]`
- `alternativeExplanations[]`
- `verificationQuestion`
- `status: inferred | unknown | user-confirmed`

不要再把 `explicit` 内容放进 hypothesis；原文明示内容直接来自 requirement 或 context。

### 5.4 `RequirementEvidenceAssessment`

逐条连接岗位要求与用户事实：

- 语义相关性。
- 角色与独立程度。
- 行动完整度。
- 结果完整度。
- 指标口径完整度。
- 相似情境与迁移距离。
- 最终确定性证据强度。
- 缺失证据和下一动作。

### 5.5 `JDQualityFinding`

记录 JD 自身的问题：冲突、模糊、过宽、缺少结果、资历与职责不一致、疑似模板化、否定条件和信息缺失。它是“需要向招聘方核实什么”的来源之一。

## 6. 建议的分析流水线

### 阶段 1：确定性文档结构

- 保留标题、章节、列表层级、行和字符偏移。
- 识别“职责、任职要求、加分项、福利、公司介绍”等章节。
- 标记必须、优先、不要求、至少、以上、熟练、主导等显式信号。
- 生成稳定 span ID，不依赖模型输出顺序。

### 阶段 2：LLM 原子语义拆解

- 在保留完整章节上下文的前提下拆成 atom。
- 只允许选择既有 span ID。
- 不直接决定最终优先级和证据强度。
- 对复合要求输出拆分理由，对无法拆分项标记待复核。

### 阶段 3：TypeScript 校验与归一化

- 验证 requirement 类原文的 atom 覆盖率。
- 检查 negation、显式 modality、重复 atom 和跨度。
- 生成稳定 requirement ID。
- 只让已校验 atom 进入后续步骤。

### 阶段 4：岗位本质与有限推断

- 从已校验 atom 确定性汇总任务、产出、能力、经验和情境。
- LLM 只生成带引用的 role hypotheses、替代解释和验证问题。
- 未知项按“是否会改变投递/简历/面试决策”排序，而不是强制填满固定九类。

### 阶段 5：逐要求事实召回与匹配

- 按要求分别进行别名、规范能力和文本召回。
- 每个要求提供自己的候选事实，不使用一个全局 Top 12。
- LLM 判断语义相关性；TypeScript 计算证据强度。
- 无证据时生成定向补证动作，不回退整个事实库。

### 阶段 6：形成用户决策

系统最后必须给出：

- 值得优先投递的依据与最大不确定性。
- 简历必须体现的 3–5 个要求。
- 当前最强的 3 个事实匹配。
- 最高价值的 3 个证据缺口。
- 向招聘方确认的 3–5 个问题。
- 面试优先准备的经历和风险边界。

这里的数量是界面摘要限制，不是丢弃底层完整数据。

## 7. 页面重构建议

JD 页面改为渐进披露的四个视图：

1. **先看结论**：岗位本质、准入门槛、核心产出、最大缺口、关键未知。
2. **逐条要求**：按门槛、任务、产出、能力、经验、情境分组；每条显示原文、解释、优先级依据、用户证据和下一动作。
3. **推断与未知**：只展示带依据的假设、替代解释和验证问题。
4. **原文审计**：显示章节、条目、覆盖 atom、待复核和遗漏风险。

用户首先看到结论和行动，研究/调试信息放在后两层。内部英文枚举全部用中文标签显示。

## 8. 评测集必须先升级

当前 [`evals/jd-depth-eval.mjs`](../evals/jd-depth-eval.mjs) 只检查 8 个 case 是否有 ID、source，以及预期关键词是否本来就包含在 source 中。它没有调用解析函数或模型，因此 `passed: true` 不代表 JD 分析通过。

### 8.1 案例分层

至少建立 40–60 个合成或获授权案例：

- 中文规范 JD、招聘网站口语 JD、整段无列表 JD、中英混合 JD。
- 产品、研发、运营、销售、职能岗位。
- 校招、1–3 年、资深、负责人。
- 复合要求、否定要求、显式优先、模糊量词、互相冲突、职责过宽。
- 信息充分、缺失团队信息、缺失成功指标、只有公司宣传。

### 8.2 Gold 标注

每个案例保存：章节、source spans、atom、kind、modality、显式优先级依据、允许的推断、必须未知的内容、关键 clarification question 和逐要求候选事实。

至少两人标注 20 个以上案例；类别、优先级和推断边界一致性不足时先修 rubric，不急着调 Prompt。

### 8.3 组件指标

| 组件 | 指标 | 首版门槛 |
|---|---|---:|
| 文档结构 | 章节/原文跨度正确率 | 100% 确定性测试 |
| 条目分类 | category Macro-F1 | >= 0.90 |
| 原子拆分 | atom precision / recall | >= 0.85 / 0.85 |
| 原文引用 | 精确跨度正确率 | >= 0.98 |
| modality | required/preferred/negated Macro-F1 | >= 0.90 |
| 原文覆盖 | requirement 条目 atom 覆盖率 | >= 0.95 |
| 推断安全 | 无依据确定性结论率 | 0 |
| 推断帮助 | 人工评审“值得验证”比例 | >= 0.80 |
| 事实召回 | gold claim Recall@3 | >= 0.90 |
| 错误匹配 | 无关事实进入强/中证据比例 | <= 0.05 |
| 决策摘要 | 人工评审可执行性 | >= 4/5 |

真实模型发布还要分 Provider、岗位类型和 JD 长度看 p50/p95，不用总体平均掩盖失败切片。

## 9. 建议版本：V1.9.5 JD 决策地图

### 批次一：修正确性与评测

- 删除位置式能力重要性和错误“隐性要求”汇总。
- 下游只使用已校验 requirement。
- 诊断分改为逐要求确定性聚合。
- 建立可运行解析器的 JD gold eval 与失败切片。

### 批次二：领域模型与执行器

- 增加 section/span/atom/modality/priorityBasis/qualityFinding。
- 稳定 ID、原文覆盖、否定与重复校验。
- 按 requirement 召回事实并确定性计算证据强度。
- 推断增加原文 ID、替代解释和决策影响。

### 批次三：决策型页面

- 先看结论、逐条要求、推断与未知、原文审计四个视图。
- 每条要求提供“补证、修改简历、准备面试、向招聘方确认”入口。
- 用真实模型跑分层评测和 Playwright 全流程。

## 10. 本版不做

- 不引入 MCP、RAG、Flowise 主流程或联网公司研究。
- 不下载完整 O*NET / ESCO 本体作为运行依赖。
- 不根据一个 JD 猜测真实团队规模、领导风格或公司内部事实。
- 不用更大的黑盒总分替代逐条证据与决策依据。
- 不在评测集建立前通过不断加 Prompt 追求主观“更深”。

## 11. 一手来源与边界

- [O*NET Content Model](https://www.onetcenter.org/content.html)：将岗位信息区分为 worker characteristics、worker requirements、experience requirements、occupational requirements、occupation-specific information 等领域，并同时描述跨职业信息和特定职业信息。
- [O*NET Questionnaires](https://www.onetcenter.org/questionnaires.html)：分别采集知识、技能、教育与训练、一般工作活动和工作情境，而不是把它们压成一个关键词数组。
- [ESCO 官方说明](https://esco.ec.europa.eu/en/about-esco)：ESCO 是多语言的职业与技能分类，并显式维护职业和技能之间的关系。
- 当前项目的更完整目标模型已经在 [`domain-model-spec.md`](./domain-model-spec.md) 中提出 `expectedBehavior`、`expectedOutput`、`businessScenario`、推断依据与替代解释；本次审查确认这些关键字段尚未真正落入运行模型。

O*NET 与 ESCO 用来校准信息分类，不代表它们可以直接替代中国招聘语境。中文职位、组织层级、职级措辞和招聘平台文风仍必须通过本项目自己的中文评测集验证。
