# 当前产品与代码审计（阶段稿）

审计基线：`main` / `v1.7.2` / `f83bb1a`。

## 1. 已存在的基础能力

- 多岗位简历版本、本机持久化、备份与恢复槽。
- PDF / DOCX 导入，结构化简历草稿。
- 全局经历证据的候选 / 确认状态。
- Bullet 稳定 ID、来源类型和证据 ID。
- JD 分析、简历诊断、匹配、补证、优化、面试准备和交付流程。
- Zod 输出校验、一次 JSON 修复、Mock / LLM 模式。
- 确定性 ATS 就绪度、DOCX / PDF 导出。
- 投递记录、面试复盘、运行 Trace、评测集和受约束工作流 Studio。
- Flowise 项目证据实验只能形成候选，不能直接写入业务数据。

这些能力证明项目已经不是单次 Prompt 包装器，而是有状态、门禁、评测和交付的本地求职工作台。

## 2. P1 可信度与数据安全问题

### 2.1 ATS 关键词得分可能虚高

`src/lib/ats.ts:62-69` 把 `input.highlightSkills` 拼进用于关键词命中的简历文本。即使该能力没有进入最终简历，也会被当作“已命中”。

建议：ATS 只评估最终交付文本；用户希望突出的能力单独展示为“偏好覆盖”，不能进入 ATS 分数。

### 2.2 新 JD 可能继续显示旧分析

`src/store/resume-store.ts:361-373` 在材料变化后只把最终简历标为 stale，没有清空或标注 `analysisResult` 的输入版本；`src/lib/workflow-progress.ts:35-52` 只要分析对象存在就判定分析完成。

后果：新 JD、旧匹配项、旧追问和旧优化建议可能混用，最终生成又使用新输入与旧中间产物。

建议：为分析记录 `inputFingerprint` / `sourceRevision`；材料变化后整个分析状态变 stale，所有页面显示“基于旧材料”，禁止继续生成。

### 2.3 Mock 可能生成与用户无关的固定简历

`src/services/ai/resumeAgent.mock.ts:315-390,482-534` 包含固定姓名、公司、时间和指标。对任意输入运行 Mock 后仍可确认并导出。

建议：Mock 必须明显标记“演示数据”，只允许在明确加载示例材料时产生示例输出；普通用户输入的 Mock 结果应基于输入做确定性转换，禁止加入输入中不存在的人名、公司和数字。

### 2.4 证据关联会产生错误可信感

`src/lib/evidence/resume-evidence.ts:67-105` 通过长度至少 2 的共同词自动关联前 3 条证据；人工编辑 Bullet 时 `updateResumeBulletText` 保留旧 `evidenceIds`。

建议：自动关联只能形成候选；数字、实体和动作必须逐项校验。任何人工修改触及实体、数字、否定、范围或时间时，将关联标记为 `needs-review`。

### 2.5 损坏数据恢复会丢失全局对象

`src/store/resume-store.ts:178-209` 的尝试恢复仅恢复文档，并把经历证据、投递和面试复盘置空。

建议：分别对 documents、evidence、applications、reviews 做独立容错解析，恢复报告明确列出保留与丢弃对象，确认后才覆盖。

### 2.6 补证重复生成会重复写入候选

`src/store/resume-store.ts:489-523` 每次生成 Bullet 都追加一条 CareerEvidence，没有幂等键，也不替换同一追问的旧候选。

建议：候选证据记录 `sourceQuestionId`；同问题重新生成时建立修订关系或替换未确认候选。

## 3. P2 逻辑与产品解释问题

- Prompt 要求追问 5–7 条、匹配 6–8 条和面试题 10 条，但 Schema 没有数量约束，空数组也可通过。
- AI 诊断分只有 0–100 类型限制，没有固定维度、权重和 rubric；UI 容易让用户误认为分数客观可比较。
- 删除 CareerEvidence 不解除 Bullet 引用，可能产生悬空关联。
- 工作流内部数组顺序与四阶段映射不完全一致，部分步骤状态可能出现语义错位。
- ATS 的量化成果项只检测“是否出现数字”，没有检测数字口径、来源和真实性。
- ATS 关键词为简单子串匹配，同义词、否定语境、技能熟练程度和要求重要性都未处理。

## 4. 本次需求与当前模型的关键差距

### 用户材料

- `UserInput` 没有目标公司名称、团队背景、公司规模与阶段。
- 公司类型是固定枚举，没有小微企业、央企、事业单位和自定义。
- “希望突出能力”没有区分岗位建议、用户偏好和已有证据。
- 补充信息没有结构化回答方向、AI 建议或证据提示。

### 职业资产

- `CareerEvidence` 是扁平条目，不支持项目结构、能力实体、熟练度、数字口径、附件、作品集和修订关系。
- 项目 / Demo 没有独立 CRUD 工作台，无法记录角色边界、决策、失败、约束、产出物。
- 没有规范标签库、同义词、分类统计或用户自定义标签治理。

### 岗位分析

- `JDAnalysis` 没有逐条原文锚点和 Requirement ID。
- 没有业务场景、工作重心、团队痛点、行业经验、汇报关系、业务线定位或置信度。
- 没有为每条要求生成面试体现方向、准备证据和反向提问。

### 补证与面试

- 用户不会回答时只有占位文案，没有提示阶梯、回答框架、示例和“帮我回忆”路径。
- 面试准备只是静态题目和建议答案，没有抽题、用户作答、评分、对照和证据回写。
- 追问数量是 Prompt 固定范围，不是根据关键要求覆盖、证据强度和用户回答质量决定。

### 简历与教育

- 优化风格固定 4 个，不能基于岗位建议、组合参数或用户自定义。
- 优化对照表不能逐条采用、拒绝或人工修改。
- 教育只有一个对象，不能增加多段教育、课程、GPA、荣誉、证书、继续教育或条件显隐。

### 公司研究与投递

- 没有独立公司情报实体、来源引用、抓取时间、可信度和冲突处理。
- 投递模块只有状态与基础统计，没有阶段耗时、失败原因、岗位族、渠道、版本效果和复盘分析。
