# 两个求职 Agent 仓库归纳摘要

> 本文件将原始仓库事实转成对 Resume Expert 的分析判断。

## 一句话定位

- **AgentMesh-JobAgent**：成熟度较高的“Agent 可调用、多平台、有确认门禁的投递执行层”。
- **ai-job-assistant**：成熟度较低但信息架构直观的“岗位采集、匹配、看板和面试题原型”。
- **Resume Expert**：三者中最强的是“个人可信事实 → JD 要求 → 简历/面试内容”的证据生产链，但投递前的岗位机会管理和外部动作协议仍然较薄。

## 最值得借鉴的五件事

1. **岗位机会收件箱**：从浏览器页面显式采集岗位，先进入待核对区，再决定是否分析、关联简历或放弃。
2. **统一的 Agent 交互协议**：所有需要用户决定的节点都返回稳定 ID、选择项、文本兜底、后续动作和幂等键。
3. **副作用前的预览授权**：未来任何真实外发动作都必须经过“完整预览 → 用户确认 → 与内容摘要绑定的授权 → 执行 → 审计”。
4. **平台能力注册表**：平台差异用声明式能力和成功证据描述，浏览器适配器彼此隔离。
5. **投递事件与漏斗**：投递状态不应只有当前值，还应保存状态事件、阶段耗时、失败原因、来源和下一动作。

## 当前不应做的事

- 不应把 Resume Expert 改造成自动海投工具；这会削弱其“事实可信与岗位定制”的核心优势。
- 不应直接复制 `ai-job-assistant` 的代码：它没有许可证，且安全、迁移、AI 校验和测试均不足。
- 不应把 AgentMesh 的云端画像、积分计费或服务端签名设计原样引入本机个人版。
- 不应现在引入 MCP。眼前的问题是内部领域模型和显式连接器边界，MCP 不是岗位采集、幂等或授权机制的替代品。
- 不应把 HR 活跃度等弱信号直接合成“值得投递”的确定分数。

## 建议的产品边界

Resume Expert 继续作为职业事实和岗位材料的唯一事实来源；新增机会层和交付协议，但把真实平台自动化放在可选连接器中：

`岗位采集 → 待核对机会 → JD/证据分析 → 选择简历版本 → 交付预览 → 人工授权 → 可选平台执行 → 审计与复盘`

第一阶段只做采集、核对、决策和模拟交付，不做真实自动投递。这样能验证价值，又不会提前承担平台条款、页面脆弱性和误投风险。
