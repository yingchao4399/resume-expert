# 产品演进复盘

## 1. 从“简历生成器”到“职业资产工作台”

项目从 V1.0 到 V1.7.2 的演进可以划分为五个阶段。

| 阶段 | 版本 | 主要变化 | 已形成的能力 | 尚未解决的问题 |
|---|---|---|---|---|
| 可交付 MVP | V1.0–V1.2 | 本地文档、编辑、导入、备份、模板、DOCX/PDF | 能完成一份岗位定制简历 | 内容可信度和长期复用能力不足 |
| 业务闭环 | V1.3–V1.5 | 证据库、四阶段、投递、面试复盘 | 从材料到交付形成闭环 | 证据仍是扁平文本，投递反馈未反哺资产 |
| 稳定性 | V1.6–V1.6.1 | 状态门禁、ATS、恢复、AI 测试、CI、模块拆分 | 已接近可以长期本地使用 | 状态与外键仍存在实际一致性漏洞 |
| 可测与透明 | V1.6.2–V1.7.0 | 合成测评集、Trace、Studio | AI 运行可观察、可回归 | 测评仍未覆盖真实证据链和全部业务决策 |
| 可实验与可编排 | V1.7.1–V1.7.2 | Flowise 实验、受约束工作流草稿/发布/回滚 | 可视化实验不会直接接管核心数据 | 编排能力领先于职业资产模型成熟度 |

这一演进方向总体正确：先完成交付，再补本地数据、可靠性、测评和透明化。当前转折点是：后续竞争力不应继续来自更多 AI 按钮，而应来自更可信的个人职业资产模型。

## 2. 当前产品的真实定位

当前 V1.7.2 更准确的定位是：

> 一个具备本地持久化、AI 结构化输出、岗位版本、简历交付、运行追踪和实验编排能力的个人简历工作台。

它还不能被描述为：

- 完整的职业能力图谱；
- 可验证的个人证据系统；
- 深度公司情报平台；
- 能自主完成求职任务的全能 Agent；
- 能预测招聘通过率的 ATS 模拟器。

## 3. 历次讨论形成的稳定原则

### 3.1 TypeScript 是业务事实来源

材料校验、状态迁移、用户确认、数据写入、导出门禁、评分和版本迁移必须由 TypeScript 执行器控制。Flowise、Skill 和模型只能返回候选结果。

### 3.2 AI 产物不能自动升级为事实

AI 生成的事实草稿、数字、能力标签、公司推断和面试答案必须保留来源、生成方式和确认状态。用户确认不是一个笼统按钮，而应以原子事实为单位。

### 3.3 简历只是职业资产的一个视图

项目、经历、能力、数字证据、面试故事和作品集内容应先存在于个人资产库，再按 JD 选择和组合为岗位简历。

### 3.4 本地优先不等于只用 localStorage

本地优先可以使用 IndexedDB、浏览器 Blob 和未来的本机 SQLite。关键是数据不依赖账号与云端，而不是永远把所有业务数据放进一个 Zustand JSON。

### 3.5 透明化不等于暴露思维链

Studio 应展示输入来源、节点、结构化输出、耗时、错误、修复、版本和用户决策，不展示模型隐藏思维链，也不能把“有 Trace”误当成“结论可信”。

## 4. 当前最重要的产品转向

下一阶段应从：

```text
简历输入 + JD → 模型分析 → 模型改写 → 导出
```

转向：

```text
原子事实与来源
→ 项目 / 经历 / Demo
→ 能力及熟练度证据
→ JD 逐条要求
→ 可信匹配与缺口提问
→ 简历 / 面试 / 作品集素材
→ 投递反馈和资产更新
```

这不是推翻已有产品。导入、编辑、版本、模板、导出、追踪、测评和工作流都可以保留；需要替换的是证据、项目、能力和岗位要求之间的底层关系。
